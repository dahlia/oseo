Package audit
=============

This audit reads the published artifacts of candidate npm packages and
reports which constructs in each package's ESM graph Oseo cannot compile
today and which wait for an M6 API group. It is the evidence behind the
corpus order in [*PLAN-PKG.md*](../../../PLAN-PKG.md). It is an inspection of
files, not an execution result: no package here has been compiled or run by
Oseo.

The table at the end is generated by *tools/package-audit.ts* from
*candidates.json*, which pins one version per package. Rerunning the audit
against the same versions should reproduce the table; a different version
is a different audit.


Procedure
---------

Install the pinned candidates into a scratch directory outside the
repository, then point the tool at the resulting *node\_modules*:

~~~~ sh
mkdir audit && cd audit && npm init -y >/dev/null
npm install --no-save --ignore-scripts --legacy-peer-deps \
  $(node -e 'const c=require("../docs/evidence/package-audit/candidates.json");
    console.log(Object.entries(c).map(([n,v])=>`${n}@${v}`).join(" "))')
cd .. && node tools/package-audit.ts --root audit/node_modules --update
hongdown --write docs/evidence/package-audit/README.md
~~~~

The last step reformats the generated table the way `mise run check:fmt`
expects. The install step needs the network. `--ignore-scripts` keeps optional
native addons such as `cbor-extract` from building; the audit never loads them.
The tool itself needs only the installed files and the repository's pinned
`@babel/parser`.

For each candidate the tool:

 -  finds the package directory by walking up from the install root and
    resolves symbolic links, so a pnpm layout yields one path per file;
 -  resolves the root entry through `exports` with the `oseo` and `import`
    conditions active and `default` always matching, visiting the
    manifest's keys in order as Node.js does, with subpath patterns matched
    by the longest prefix; falls back to `main` only when `exports` is
    absent;
 -  classifies each file as ESM or CommonJS by extension and otherwise by
    the `type` field of the nearest enclosing *package.json*, so a nested
    manifest such as *browser/package.json* in `yaml` counts;
 -  parses every reached ESM file with `@babel/parser` and follows its
    static `import` and `export … from` specifiers transitively, including
    into dependencies and `#` imports, requiring an exact file for relative
    specifiers;
 -  records every reference to a name the file does not declare and that
    Oseo lacks: `Buffer`, `process`, `__dirname`, `__filename`, `global`,
    `module`, `exports`, `Intl`, and the web globals listed below, with the
    line and whether the reference is at module top level or inside a
    function body;
 -  records `import()`, `eval()`, `import.meta`, `node:` imports, and the
    forms that reach the `Function` constructor: `new Function(…)`,
    `Function(…)`, an alias such as `const F = Function`, and
    `(function () {}).constructor`.

Only static imports are followed. CommonJS files end the walk at that file,
and `require()` targets are not resolved. `.json` imports are counted as
reached files but not inspected.


Reading the table
-----------------

Each row names the package and the version inspected, the ESM entry the
resolver selected relative to the install root, how many files the walk
reached, how many distinct dependency packages were entered split by format,
every blocker with its location, the earliest M6 group among the web globals
found, and a verdict.

The M6 group numbers are the dependency-ordered groups of
[*PLAN-M6.md*](../../../PLAN-M6.md): 1 encoding and URLs, 2 events and abort
signals, 3 timers, `performance`, and `structuredClone`, 4 `Blob`, `File`,
and `FormData`, 5 streams, 6 `Headers`, `Request`, `Response`, and `fetch()`,
7 Web Crypto, 8 WebAssembly, and 9 remaining globals including `atob` and
`btoa`.

The verdicts mean:

 -  `CLEAN`: the selected graph is ESM throughout and references nothing
    Oseo lacks. The package is a resolver-only target.
 -  `NEEDS-M6-GROUP-n`: the graph is otherwise clean but references web
    globals; `n` is the earliest group it waits on. A reference inside a
    function body fails only when that function runs, so a scenario that
    avoids it can still succeed before group `n` lands.
 -  `BLOCKED (…)`: the entry is CommonJS, the graph reaches a CommonJS file
    or dependency, or it contains a construct outside the profile: a
    `node:` import, a Node.js global, `Intl`, `import.meta`, `import()`,
    `eval()`, or a `Function` constructor form. The reasons are listed in
    the order found.
 -  `UNCHECKED (…)`: the package was not installed or the installed version
    differs from *candidates.json*.

Two Oseo-specific facts matter when reading the blocker column. First,
`import()` and `eval()` are rejected when a module is parsed, so a call in a
function that is never invoked still blocks the whole graph. Second, a read
of an undeclared global compiles to a run-time `ReferenceError`, and a
`typeof` guard on it evaluates to `"undefined"`, so `Buffer` or `Intl`
inside a function body blocks only the paths that reach it. The verdict
treats every such reference as a blocker because the audit cannot know which
paths a scenario takes; the `top-level` and `function-body` tags let a
reader refine that per scenario. Plain uses of the `Function` global such
as `x instanceof Function` or `Function.prototype.call` work and are not
reported; only the constructor forms are.


Limits
------

Declared names are collected per file without modelling scope, so a file
that declares its own `process` function hides the global everywhere in that
file. This errs toward fewer reports. The walk does not evaluate conditions,
so a reference guarded by `typeof` is still listed. Yarn Plug'n'Play layouts
are not supported; use the `node-modules` linker. The audit does not inspect
TypeScript sources a package may ship beside its JavaScript, and it does not
check whether a dependency's version satisfies the importer's range.


History
-------

The first version of this audit was produced on 2026-11-02 during a survey of
early package targets. The checked-in tool corrects three defects of that
version: it reads the module format from the nearest *package.json* rather
than the package root, which had classified the ESM build of `yaml` as
CommonJS; it
detects `Function` constructor aliases and `(function).constructor`, which
had let zod and eta pass as free of dynamic source; and it selects export
conditions in manifest key order rather than in a fixed preference order.
